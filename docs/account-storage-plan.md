# 城影记 · 账号与原图存储依据

更新：2026-09-21。本文件保留阶段 3 的存储决策、用户可见行为及容量证据。具体组件已在 [技术方案](tech-stack.md) 选定，字段、会话和恢复接口见 [数据设计](data-api-design.md)，不再重复维护另一套实现说明。

## 已确定的保存方式

本地开发时由本机应用服务管理账号、数据库和私有原图目录；上线后迁移数据库与原图到服务器。用户已确认需要独立副本和部署后的跨电脑访问，照片不依赖原 U 盘持续连接。

| 场景 | 应有结果 |
| --- | --- |
| 从电脑或 U 盘添加 | 系统保存完整原图副本，保留源文件 |
| 保存成功后移走源文件 | 系统仍从自己的私有目录读取副本 |
| 排序、写文字、跨影集移动 | 改数据库资料，照片 ID 和原图字节保持不变 |
| 重启或换浏览器 | 已保存账号、空影集、照片、顺序和文字仍在 |
| 换账号 | 私人列表和原图读取均只允许访问所属账号内容 |
| 删除与恢复 | 系统副本进入 30 天回收站，不影响源文件；恢复保留文字 |
| 上线后换电脑 | 登录同一账号读取服务器中的同一份资料，不必再次导入 |

## 数据分工与成功条件

数据库保存账号、会话、影集、照片标识、顺序、文字与状态；原图存放在公开静态资源目录之外。原文件名只用于显示和编号辅助，不作为文件唯一键，也不把源绝对路径变成网页地址。

逐文件暂存完成不等于影集已保存。完整文件校验通过、资料成功提交后才显示“已加入影集”；失败可重试，数据库和文件之间的故障补偿按阶段 6 执行。普通列表及城市点亮仅计算有效照片，暂存文件和回收站分别处理。

同名或同内容文件不覆盖，重复照片交由本人查看决定。原图由鉴权接口提供，不使用永久公开静态地址；空影集、上传、排序、文字、回收站和原图读写都核对归属。实现与安全资料来源集中在技术方案中。

## 容量证据与备份

2026-09-20 的 23 张样本合计 82,993,868 字节，平均约 3.61 MB；外推单账号 3000 张约 **10.83 GB**，再保留一份完整备份约 **21.66 GB**。还需预留回收站、上传暂存、数据库与增长空间；不是全部账号用量或产品上限。

当日只读检查 D 盘约有 520.76 GB 可用，未发现这组样本估算下的本地空间障碍。该记录不是现在的磁盘状态，也不证明已经保存 3000 张或通过多人读写；本轮不重新读取用户照片或查询磁盘。

备份须包含数据库、有效原图和未到期回收站，并在维护窗口协调上传、修改和清理；保存在独立介质，不能只复制数据库或在同一磁盘留另一份照片。备份恢复需核对数量、归属、顺序、文字、文件哈希及过期状态，并撤销旧会话。具体步骤见技术和数据设计，备份频率、介质与保留策略在正式使用前落实。

## 尚未验收的内容

上述保存行为是已选方案，当前原型只有内存演示，不能证明真实认证或持久化。两账号越权、原图保存失败、重启保留、回收站竞争、备份恢复、400/3000 规模和跨电脑访问仍需开发后验证。任务归属见 [开发计划](development-plan.md)，已有小样证据见 [可行性记录](feasibility.md)。
