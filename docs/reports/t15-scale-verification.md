## 本轮修改与失败诊断

1. **开发代理连接池**：首次页面 400 张上传时出现本机代理 `connect ETIMEDOUT`，最终仅 395 项 staged、5 项 pending，未能保存，因此判为失败。核对 Vite 所用代理实现确认默认 `agent=false` / `Connection: close`；现增加 `keepAlive`、最多 8 个连接、2 个空闲连接的有界池。修复后的复测 400 个响应全部 200，不通过自动重试隐藏错误。这改善开发环境连续请求连接复用，不将底层操作系统丢包原因或所有网络故障归因于同一个问题。[Node HTTP Agent](https://nodejs.org/docs/latest-v24.x/api/http.html#class-httpagent)
2. **原图释放加固**：组件卸载图片时显式断开 `img.src`，再沿用 AbortController 和 Blob URL 撤销。引用回调需要在 StrictMode 的 setup→cleanup→setup 后恢复源地址；第一版清理实现未恢复，诊断发现 naturalWidth=0 后修正。既有 Edge 浏览测试增加“被卸载的旧图片 src 为 null”断言，图片加载、切换、退出仍通过。不压缩或生成缩略图。[React 引用回调及 StrictMode](https://react.dev/reference/react-dom/components/common#ref-callback)
3. **内存测量纠偏**：初版 20 轮采样出现私有内存从约 0.9 GiB 涨至 2.37 GiB 后回落，而 JS 堆约 11 MiB、DOM 500、Blob URL 3 保持稳定，窗口中位数门槛失败；不能据此直接断言 JS 泄漏。排查还发现 SPA 的 `networkidle` 可能沿用旧状态，以及空图片集合的 `every()` 可误判就绪。最终固定滚动位置、逐个等待近视口图片 `naturalWidth > 0`，并记录 20 轮预热 + 20 轮观察的全程采样峰值，再比较同状态窗口；不刷新页面、不施加人为系统内存压力。门槛仍为 Edge 窗口增量 <256 MiB、JS <32 MiB、DOM <1000；增加预热不是把原失败记录删除。
4. **采样竞争**：CDP 枚举后某个 Edge 工具进程可能已经退出；现在最多重新枚举两次，再失败则测试失败。不把缺失内存填 0，记录重取次数。
5. **依赖类型与补丁**：新增 Node 24 的 `@types/node@24.19.1`（其类型依赖 `undici-types@7.24.6`）及 Node 配置的显式 types，修复 HTTP Agent 构建类型缺失。审计同时发现既有 PostCSS 间接依赖 `source-map-js@1.2.1` 的拒绝服务告警，仅定向更新至兼容 **1.2.2**，没有全量 `audit fix` 或框架升级；更新后 audit 零告警、构建产物哈希不变。[维护者 1.2.2 发布记录](https://github.com/7rulnik/source-map-js/releases/tag/v1.2.2)

6. **缩短排序写锁**：另一轮完整导入后的双账号基准中，文字 p95 达 **1342 ms**（超标），排序 p95 **911.901 ms**，测试失败。400 张原算法在写锁内逐条发起 800 次 ORM 更新；现在同一 Session 事务中先一次集合位移到旧最大位置之上，再用一条预编译语句的 `executemany` 分配最终位置。保留账号/影集/状态过滤、版本检查及相同事务内的影集版本更新，避免数百次 Python ORM 编译/调度占用写锁；不是把 400 行回写误称为只改两行。新增 400 张稀疏位置、其他影集不变、两次游标调度及 4/400 张第二阶段实际写入一条后故障的完整回滚检查。[SQLAlchemy 参数化批量执行](https://docs.sqlalchemy.org/en/20/core/connections.html#sqlalchemy.engine.Connection.execute)

隔离服务、合成图片生成、HTTP 负载/审计、Windows 内存采样与 Edge 测试均在专用工具目录；`npm run test:scale` 显式启用，不拖慢日常默认套件。五个工具单元测试覆盖 p95 算法、非隔离路径、缺失/错误标记及服务身份不符时拒绝继续。正式 API 契约、数据库结构和版本没有变化，仍为 0.13.0 / `b61e24f803a7`。

## 验证口径与边界

- 400 张页面全分页核对 ID 唯一、文件名和顺序；服务端另逐本核对所有照片。两账号各 30 轮首批资料、统计、文字与排序；原图抽取 20 次核对传输哈希，越权原图均 404；同影集同版本实际竞争只允许一个 200，另一个 409，最后恢复完整顺序。
- 3000 张逐份进入回收站，30 次首批查询及完整分页核对删除时间/ID 顺序，无遗漏或重复；第二账号仍为 400 张且回收站为空；逐本按原顺序恢复全部照片。
- 在线审计和停止服务后的审计均对 **3400 份源文件 + 3400 份系统副本**逐个 SHA-256 比对，同时检查大小、尺寸、归属、文字、连续位置、SQLite 完整性与外键。不是只查数据库中的哈希字段。
- 服务停止后获取正式维护锁，实跑 30 轮清理：保留原有 200 条文件检查界限和完整目录枚举逻辑，覆盖当前 3400 份有效原图；要求无失败、无忙跳过、无有效照片/文件误删。本轮不制造大规模到期积压，不把空删除负载称为数千份过期删除性能已通过。
- 内存取 CDP 返回的本次独立 Edge 进程 Windows 私有字节总和及后端进程；不读取用户浏览器。2 秒采样可能漏掉瞬时峰值，工作集总和含共享页重复计数；主要使用私有字节。JS 堆/DOM 在每个同状态点经 GC 后测量，周期采样不强制 GC；不同进程内存回收节奏不等于 Blob/DOM 泄漏。没有模拟系统内存压力来促使结果达标。
- 图片就绪观测使用 `naturalWidth`，不是 `img.decode()`、逐帧绘制检查或精确解码计时；原始结果中的 `originalDecodeMs` / `throttled12MpDecodeMs` 是该观测的历史字段名。计时包括自动点击、等待资料与轮询，HTTP 元数据单独测，不与图片下载混为一谈。p95 为 nearest-rank；均为本机结果，不是公网 SLA。
- 保留已知边界：两账号并发不是十人容量证明；40 轮不是数小时 soak 或永不泄漏承诺；合成内容不是用户真实拍摄素材覆盖；无断电演练、外网延迟承诺或实际备份介质验收。T16/T17 继续按计划，不提前标记完成。
